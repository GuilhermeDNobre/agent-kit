# Runtime: T3 Code

How the coordinator runs workers on **T3 Code**. Imported by `CLAUDE.md`. The workflow rules
(what to dispatch, when to verify, when to escalate) come from `agent-kit wf`; this file only says
how each step maps onto T3 tools.

## Tools used

| Step | T3 tool | Notes |
|---|---|---|
| Discover providers and models | `orchestrator_capabilities` | Once per thread before the first dispatch; `/configurar-worker` stores the choice in `.agent-kit/config.json` |
| Dispatch a worker | `delegate_task` | Pass the `call.args` printed by `agent-kit wf dispatch` **unchanged** |
| Read a finished worker | `task_status` | Only after its completion wakes you, on resume, or for an overdue task |
| Stop a worker | `task_cancel` | Use the `runtimeCall` printed by `agent-kit wf cancel` |
| Follow up on a finished child | `t3_thread_send` | Rare: a send to a finished child starts a fresh task — record it with `wf started` |

The child receives **only** the `task` text. It has no access to this conversation. That is why
the brief generated by `wf dispatch` inlines everything the worker needs.

## Dispatch

```bash
agent-kit wf next <run>                    # lists "dispatch": [task ids]
agent-kit wf dispatch <run> <task>         # prints { call: { tool: "delegate_task", args } }
```

1. Call `delegate_task` with exactly `call.args` (`task`, `title`, `role`, `mode: "async"`,
   `isolation`, `clientRequestId`, `target`).
2. Record the returned id: `agent-kit wf started <run> <task> --ref <taskId>`.
3. Dispatch every task listed in `dispatch` before ending the turn; the scheduler already applied
   dependencies, the worker cap and file ownership.
4. End the turn. **Do not poll** `task_status` and do not loop with sleeps: T3 wakes the coordinator
   when a child finishes.

If `delegate_task` errors or times out, call it again with the **same** `clientRequestId` — it is
T3's retry key and prevents a duplicate worker. `wf dispatch` on a task that is running without a
recorded ref prints the same call again.

## Collecting a result

When a child's completion arrives:

1. `task_status` with its `taskId` → `summary` is the worker's final message.
2. Save the summary to `.agent-kit/runs/<run>/inbox/<task>.md` and record it:
   `agent-kit wf report <run> <task> --file .agent-kit/runs/<run>/inbox/<task>.md`.
3. Follow the `next` field of the output (`verify`, `redispatch`, `resolve-blocker`, …).

## Overdue and lost workers

`wf next` lists `overdue` tasks (no progress for `taskTimeoutMinutes`). A timeout is **not** proof
that a worker died:

1. Call `task_status` once for its ref.
2. `working` / `waiting_for_children` → `agent-kit wf touch <run> <task> --note "<what you saw>"`.
3. `result_available` → collect it as above.
4. Error, unknown task, or clearly stuck → `task_cancel`, then
   `agent-kit wf lost <run> <task> --reason "<evidence>"` (counts as a failed attempt).

## Resume after an interruption

`agent-kit wf resume <run>` prints:

- `reconcile`: running tasks with a T3 ref → call the printed `task_status` once each and act as in
  "Overdue".
- `redispatchSameKey`: dispatched but never confirmed → `agent-kit wf dispatch <run> <task>` prints
  the same call with the same `clientRequestId`; T3 deduplicates.
- `foreign`: attempts started under another runtime (e.g. Orca) → check them there, or
  `wf lost` them with the evidence, before redispatching here.

## Isolation

`.agent-kit/config.json` → `runtimes.t3.isolation`:

- `shared` (default): children edit the parent checkout. Parallel tasks never share files (the
  scheduler enforces it), and the coordinator sees the changes directly.
- `worktree`: each child gets a checkout from the parent **commit**. Uncommitted work — including
  earlier tasks' output — is invisible to it, and its changes must be integrated before review.
  Use it only when tasks are long and fully independent and local commits are allowed.

## Linear through T3

With `tracker.kind: "linear"` and `tracker.linear.via: "t3"` (the default on this runtime), Linear is
reached through T3's issue tools — no API key. `agent-kit` prints the calls; you make them:

1. `wf new` prints one `create_issue` for the parent. Call it, then
   `agent-kit wf tracker-bind <run> _parent --key <key> --url <url>`.
2. `agent-kit wf sync <run>` prints one `create_issue` per task (the body says `Parte de <parent>`
   and carries the `agent-kit-task` block). Call each, bind each with `wf tracker-bind <run> <task>`,
   and call `link_issue` for every issue you create.
3. At every checkpoint (after dispatches, reports, gates, completion), `agent-kit wf sync <run>`
   prints `set_issue_state` / `comment_on_issue` calls grouped per issue. Make them, then run the
   printed `agent-kit wf sync <run> --ack <ids>`. Unacknowledged events are printed again next time.

Every printed `create_issue` carries `project: <tracker.linear.project.name>`: all issues of this
repository belong to its dedicated Linear project, isolated from other projects. If T3's
`create_issue` does not accept a project, the T3 project's Linear connection must point at that
Linear project — confirm it in `/configurar-worker` and never create the issues elsewhere.

State names come from `tracker.linear.stateNames` (defaults: `Todo`, `In Progress`, `Done`,
`Canceled`); `read_issue` lists the team's real states if you need to change them. T3's issue
tools have no sub-issues or relations, so hierarchy and dependencies are written in the issue body.

## Review

The `review` profile defaults to `provider: "coordinator"`: you review, and you record
`--reviewer coordinator`. To review with another model, dispatch a `delegate_task` with
`role: "review"` and that profile's target, then record its verdict with that executor id. The
reviewer must differ from the implementer.

## Limits

Worker models run on the provider configured in the profiles (Antigravity by default). Their quotas
are real and not unlimited: keep `maxWorkers` modest, use the `fast` profile for mechanical work,
and treat rate-limit failures as failed attempts (the retry ladder escalates them).
