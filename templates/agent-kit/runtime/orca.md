# Runtime: Orca

How the coordinator runs workers on **Orca**. Imported by `CLAUDE.md`. The workflow rules (what to
dispatch, when to verify, when to escalate) come from `agent-kit wf`; this file only says how each
step maps onto `orca orchestration`. The coordinator itself runs in an Orca terminal.

Before the first dispatch of a session, load the version-matched guide once:
`orca skills get orchestration`. It wins over this file on Orca's own mechanics.

## Commands used

| Step | Orca command | Notes |
|---|---|---|
| Bind a Run | `orca orchestration run-current` / `run-create --environment local --objective "…"` | One Orca Run per agent-kit run |
| Dispatch a worker | `orca orchestration worker-start --environment local --spec-file <brief> --agent <id> --model <id> --worktree current` | Printed by `agent-kit wf dispatch`; run it **unchanged** |
| Inspect a worker | `worker-show --dispatch <id>`, `worker-read --dispatch <id>` | Only on resume or for an overdue task |
| Steer or follow up | `orca orchestration send --to dispatch:<id> --subject … --body-file …` | Works in any state; a finished worker gets it as a follow-up task |
| Answer a question | `orca orchestration reply --id <message_id> --body-file …` | |
| Stop a worker | `orca orchestration worker-stop --dispatch <id>` | Printed by `agent-kit wf cancel` |

The worker receives **only** its spec — the brief file — plus Orca's preamble (task and dispatch
ids, how to send `worker_done`). It has no access to this conversation; that is why the brief
generated by `wf dispatch` inlines everything.

## Dispatch

```bash
agent-kit wf next <run>                    # lists "dispatch": [task ids]
agent-kit wf dispatch <run> <task>         # prints { call: { kind: "shell", commands: [...] } }
```

1. Once per agent-kit run, make sure an Orca Run is bound (`run-current`; if none,
   `run-create --environment local --objective "<objective>"`).
2. Run the printed `worker-start`. Record the returned dispatch id:
   `agent-kit wf started <run> <task> --ref <dispatch_id>`.
3. Start every task listed in `dispatch` before ending the turn — up to ~4 starts from one shell
   command (`orca skills get orchestration --reference references/parallel-start.md`). The
   scheduler already applied dependencies, `maxWorkers` and file ownership.
4. **End the turn.** Orca wakes the coordinator when a worker sends `worker_done`, a `question` or
   an `escalation`.

Never:

- poll `orca orchestration check` or arm a watch script — a script's `check` takes the mail, so
  Orca has nothing left to wake you with;
- read or steer a worker through its terminal — use `worker-read` and `send`;
- rerun a failed `worker-start`. Read `failedStage` and do only what the CLI prints; it names a
  `--retry-request` id when a replay is safe;
- create checkouts yourself — `worker-start --worktree new-child` creates them.

## Collecting a result

When a `worker_done` wakes you:

1. Its body carries the worker's final message with the `agent-kit-report` (or `agent-kit-review`)
   block. Save it to `.agent-kit/runs/<run>/inbox/<task>.md`.
2. `agent-kit wf report <run> <task> --file .agent-kit/runs/<run>/inbox/<task>.md` (gates:
   `agent-kit wf review <run> <task> --gate <gate> --file … --reviewer <executor>`).
3. Follow the `next` field of the output (`verify`, `redispatch`, `resolve-blocker`, …).

A `question`: answer with `reply` when the answer follows from the plan or the user's instructions;
otherwise follow the escalation rules in `CLAUDE.md`. An `escalation` with `stopReason`: the worker
stopped without `worker_done` — see "Overdue and lost workers".

Finished workers close on their own. Lost track of mail? `orca orchestration inbox --terminal
run:<orca_run_id> --limit 50` shows what `check` already handled.

## Overdue and lost workers

`wf next` lists `overdue` tasks (no progress for `taskTimeoutMinutes`). Silence, a timeout or
`unverifiable` liveness is **not** proof that a worker died:

1. `orca orchestration worker-show --dispatch <id> --json` (the call printed by `wf resume`).
2. Still working, or parked on a human prompt (`observation.agentWait`) → resolve the prompt if
   needed, then `agent-kit wf touch <run> <task> --note "<what you saw>"`.
3. Finished with a `worker_done` you missed → read it from the `inbox` and collect it as above.
4. `stopReason: exited` (exit confirmed) or clearly stuck → `worker-stop`, then
   `agent-kit wf lost <run> <task> --reason "<evidence>"` (counts as a failed attempt). For `lost`
   with `unverifiable` liveness, report the uncertainty instead of retrying.

## Resume after an interruption

`agent-kit wf resume <run>` prints:

- `reconcile`: running tasks with a dispatch id → run the printed `worker-show` once each and act
  as in "Overdue".
- `redispatchSameKey`: dispatched but never recorded → check `orca orchestration worker-list` first;
  record an existing dispatch with `wf started`, otherwise `agent-kit wf dispatch <run> <task>`.
- `foreign`: attempts started under another runtime (e.g. T3) → check them there, or `wf lost` them
  with the evidence, before redispatching here.

Attempts recorded before agent-kit 0.4 carry a `<terminal>|<task>` ref; `wf cancel` and `wf resume`
print the old terminal commands for them.

## Workspaces

`.agent-kit/config.json` → `runtimes.orca`:

- `worktree: "current"` (default): workers edit the coordinator's worktree. Parallel tasks never
  share files (the scheduler enforces it), and the coordinator sees the changes directly.
- `worktree: "new-child"`: each implementation task gets a child worktree. Its changes must be
  integrated before review, and a new worktree branches from the pushed base — pushing is a
  protected action unless `autonomy.permissions.push` is true. Gates always run in the current
  worktree.
- `keepOpen: true`: workers stay open after finishing, for a user who wants to watch or talk to
  them.

## Linear through Orca

With `tracker.kind: "linear"` and `tracker.linear.via: "orca"` (the default on this runtime), the
CLI reaches Linear through Orca's own connection (`orca linear …`) — no API key. Sync is automatic
after every `wf` command, like the API mode:

- every issue is created in the repository's dedicated Linear project
  (`tracker.linear.project`), in team `tracker.linear.teamKey`, labelled `agent-kit`;
- the run becomes a parent issue, each task a real sub-issue (`--parent`), and `dependsOn` becomes
  `blocks` relations;
- each transition sets the mapped status (`tracker.linear.stateNames`) and adds a comment.

The Orca CLI cannot create projects. When the project is missing, agent-kit creates it through the
API if `LINEAR_API_KEY` (or `tracker.linear.apiKeyEnv`) is set; otherwise the sync reports it and
the user creates it once in Linear. Tracker failures never stop a run: events stay queued until
`agent-kit wf sync <run>` delivers them.

## Review

The `review` profile defaults to `provider: "coordinator"`: you review, and you record
`--reviewer coordinator`. Gates on another profile are dispatched with `agent-kit wf gate`, which
prints a `worker-start` for that profile. The reviewer must differ from the implementer.

## Limits

Worker models run on the agents configured in the profiles. Their quotas are real: keep
`maxWorkers` modest, use the `fast` profile for mechanical work, and treat rate-limit failures as
failed attempts (the retry ladder escalates them). From Git Bash, prefix `MSYS_NO_PATHCONV=1` when
passing slash-prefixed text or POSIX paths to `orca`.
